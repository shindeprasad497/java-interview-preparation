### Q1. Detail the JVM ClassLoader Subsystem and Delegation Model.
**Answer:**
The ClassLoader subsystem dynamically loads compiled `.class` files into memory during runtime.

1. **Hierarchy (Delegation Model)**:
   - **Bootstrap ClassLoader**: Native C++ loader built into the JVM core. Loads base JDK classes (`java.lang.*`, `java.util.*` from `java.base`).
   - **Platform / Extension ClassLoader**: Loads platform extensions and JDK modular packages.
   - **Application / System ClassLoader**: Loads classes located on the application `CLASSPATH` or module path.
   - **Custom ClassLoaders**: User-defined loaders for loading classes dynamically from databases, network sockets, or encrypted archives.
2. **Delegation Principle**:
   When a class is requested, a ClassLoader first delegates the request upward to its parent. Only if the parent fails to locate the class (`ClassNotFoundException`) does the child attempt to load it itself.
3. **Phases of Loading**:
   - **Loading**: Reads binary byte stream and creates `java.lang.Class` object in Metaspace.
   - **Linking**:
     - *Verification*: Ensures bytecode adheres to JVM safety and formatting specifications.
     - *Preparation*: Allocates memory for `static` fields and initializes them to default values (`0`, `null`).
     - *Resolution*: Replaces symbolic references in the constant pool with direct memory references.
   - **Initialization**: Executes `static` initializers and assigns explicit static field values in textual order.

### Q2. Explain Heap Memory vs. Metaspace vs. JVM Stack.
**Answer:**

| Memory Region | Scope | Contents Stored | Managed By | Overflow Error |
| :--- | :--- | :--- | :--- | :--- |
| **Heap** | Shared across all threads | All objects, arrays, and instance variables | Garbage Collector | `java.lang.OutOfMemoryError: Java heap space` |
| **Metaspace** | Shared across all threads | Class metadata, method bytecodes, runtime constant pool | Native OS Memory (OS page allocator) | `java.lang.OutOfMemoryError: Metaspace` |
| **JVM Stack** | Thread-private | Stack frames (local variables array, operand stack, frame data) | LIFO push/pop on method call/return | `java.lang.StackOverflowError` |
| **Code Cache** | Shared across all threads | Native CPU machine code generated by the JIT compiler | JVM Code Cache Manager | `java.lang.OutOfMemoryError: CodeCache` |

### Q3. How does the JIT Compiler work? What are C1, C2, and Escape Analysis?
**Answer:**
The HotSpot JVM combines an **Interpreter** (instant startup, slow execution) with a **Just-In-Time (JIT) Compiler** (dynamic runtime optimization for hot code paths).

1. **Tiered Compilation**:
   - **Interpreter**: Executes initial bytecode while recording invocation counters and loop backedge counters.
   - **C1 (Client Compiler)**: Compiles hot methods quickly with light profiling and basic optimizations.
   - **C2 (Server Compiler)**: Ingests profiling data to perform aggressive global optimizations:
     - **Method Inlining**: Replaces method call overhead with the actual method body.
     - **Loop Unrolling**: Eliminates loop boundary checks.
     - **Dead Code Elimination**: Removes unreachable branches.
     - **Devirtualization**: Replaces polymorphic virtual dispatch with direct static calls when only one concrete implementation exists.
2. **Escape Analysis**:
   The JIT compiler analyzes the scope of an object. If an object created inside a method never escapes the method boundary or thread:
   - **Scalar Replacement**: The object is disassembled into primitive variables stored directly in CPU registers/Stack frames, avoiding heap allocation completely!
   - **Lock Elision**: If a synchronized lock is acquired on an object that never escapes the current thread, the synchronization overhead is stripped away.

## 2. Garbage Collection (GC) Architecture & Tuning

### Q4. Compare modern Garbage Collectors: G1 GC vs. ZGC vs. Parallel GC.
**Answer:**

```
+-----------------------------------------------------------------------------------+
|                                 G1 GC HEAP LAYOUT                                 |
+-----------------------------------------------------------------------------------+
|  [ Eden ] [ Free ] [ Old  ] [ Surv ] [ Eden ] [ Old  ] [ Humongous ] [ Free ]     |
|  [ Old  ] [ Surv ] [ Eden ] [ Free ] [ Old  ] [ Eden ] [ Free      ] [ Old  ]     |
|  (Heap divided into ~2048 equal regions: 1MB to 32MB each)                        |
+-----------------------------------------------------------------------------------+
```

| Garbage Collector | Target Workload | Latency (STW Pause) | Throughput | How It Works |
| :--- | :--- | :--- | :--- | :--- |
| **Parallel GC** | Batch processing, ETL, offline jobs | High (50ms - 5s+) | Maximum | Multi-threaded Mark-Sweep-Compact. Freezes all app threads during GC. |
| **G1 GC** (Default Java 9+) | General enterprise web apps, balanced throughput/latency | Configurable (100ms - 200ms) | High | Divides heap into ~2048 regions (Eden, Survivor, Old, Humongous). Prioritizes regions with most garbage ("Garbage-First"). |
| **ZGC** (Production ready Java 15+) | Ultra-low latency microservices, large heaps (16MB - 16TB) | < 1ms predictable | Good (~90-95% of G1) | Concurrent Mark, Relocate, and Compact using **Colored Pointers** and **Load Barriers**. STW pauses do not increase with heap size. |

### Q5. What are the essential JVM tuning and diagnostic flags?
**Answer:**

```bash
# Heap Sizing
-Xms4g -Xmx4g               # Set min & max heap equal to prevent heap resize overhead
-XX:MetaspaceSize=256m       # Initial Metaspace size
-XX:MaxMetaspaceSize=512m    # Prevent Metaspace from consuming all host RAM

# GC Selection & Tuning
-XX:+UseG1GC                 # Enable G1 Garbage Collector (default in Java 9+)
-XX:MaxGCPauseMillis=200     # Soft target maximum GC pause time
-XX:InitiatingHeapOccupancyPercent=45 # Trigger concurrent marking when Old Gen reaches 45%

# Production Diagnostics & Crash Dumps
-XX:+HeapDumpOnOutOfMemoryError          # Dump heap to file automatically on OOM
-XX:HeapDumpPath=/var/log/app/heapdump.hprof
-Xlog:gc*,gc+phases=debug:file=/var/log/app/gc.log:time,uptime,pid:filecount=5,filesize=50M
```

## 3. Modern Java Features (Java 8 to 21 LTS)

### Q6. Stream API Deep Dive: Intermediate vs. Terminal Operations & Parallel Stream Hazards.
**Answer:**
- **Intermediate Operations (Lazy)**: Return a new `Stream` and do not execute until a terminal operation is invoked (`map`, `filter`, `flatMap`, `sorted`, `distinct`, `peek`).
- **Terminal Operations (Eager)**: Consume the stream pipeline and produce a result or side-effect (`collect`, `count`, `forEach`, `reduce`, `anyMatch`, `findFirst`).

```java
// Complex Stream API aggregation
Map<Department, List<String>> highEarnersByDept = employees.stream()
    .filter(e -> e.salary() > 100_000)
    .collect(Collectors.groupingBy(
        Employee::department,
        Collectors.mapping(Employee::name, Collectors.toList())
    ));
```

> [!WARNING]
> **Why Parallel Streams are Dangerous in Web Servers**:
> `stream().parallel()` executes tasks on the shared common `ForkJoinPool.commonPool()`. If a blocking database query, REST call, or file I/O task runs inside a parallel stream, it starves the shared pool, blocking unrelated request threads across the entire Spring Boot application!

### Q7. Explain Records (Java 16) and Sealed Classes (Java 17).
**Answer:**

#### 1. Records (`record`):
Transparent, immutable data carriers. The compiler automatically generates `final` fields, canonical constructor, accessors, `equals()`, `hashCode()`, and `toString()`.

```java
public record OrderRequest(
    String orderId,
    @NotNull BigDecimal amount,
    List<String> items
) {
    // Compact constructor for validation and defensive copying
    public OrderRequest {
        if (amount.compareTo(BigDecimal.ZERO) <= 0) {
            throw new IllegalArgumentException("Amount must be positive");
        }
        items = (items != null) ? List.copyOf(items) : List.of();
    }
}
```

#### 2. Sealed Classes (`sealed`, `permits`):
Restricts domain class hierarchies by explicitly declaring which subclasses can extend or implement a type.

```java
public sealed interface PaymentResult
    permits PaymentSuccess, PaymentFailed, PaymentPending {}

public record PaymentSuccess(String txId, BigDecimal amount) implements PaymentResult {}
public record PaymentFailed(String errorCode, String reason) implements PaymentResult {}
public record PaymentPending(String trackingUrl) implements PaymentResult {}
```

### Q8. What are Virtual Threads (Project Loom - Java 21 LTS)?
**Answer:**

```
[ Traditional Platform Threads (1:1 with OS Threads) ]
 Thread 1 --------> OS Thread 1 (Stack: 1MB, Expensive context switch, Max ~3,000)
 Thread 2 --------> OS Thread 2

[ Virtual Threads (M:N with OS Carrier Threads) ]
 Virtual Thread 1 ---\
 Virtual Thread 2 ----- Carrier Thread A (ForkJoinPool) ---> OS Thread A (Stack: KB)
 Virtual Thread 3 ---/
```

1. **How It Works**:
   - **Platform Threads**: Bound 1:1 to OS kernel threads. Memory footprint is ~1MB per thread stack. Creating 10,000 platform threads exhausts OS memory.
   - **Virtual Threads**: Lightweight user-mode threads managed directly by the JVM. Their stack frames are allocated on the Java heap (~few KB). Millions of virtual threads can run simultaneously.
   - When a Virtual Thread encounters a blocking I/O operation (e.g., JDBC query, HTTP request, socket read), the JVM unmounts it from the underlying **Carrier Thread** (OS thread) and parks it on the heap. The carrier thread immediately executes other virtual threads!
2. **Thread Pinning Pitfall**:
   A Virtual Thread cannot unmount from its carrier thread if it blocks inside:
   - A `synchronized` block/method (Replace with `ReentrantLock`!).
   - A native JNI call or Foreign Function interface call.

```java
// Enabling Virtual Threads in Spring Boot 3.2+ (application.properties):
// spring.threads.virtual.enabled=true

// Manual Virtual Thread Executor creation
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    IntStream.range(0, 100_000).forEach(i -> {
        executor.submit(() -> {
            Thread.sleep(Duration.ofSeconds(1)); // Non-blocking parking!
            return i;
        });
    });
}
```

## 4. Senior Production Scenarios & Incident Walkthroughs

### Scenario 1: Diagnosing a Production Memory Leak
**Interview Question**: *"Your service is crashing with `OutOfMemoryError: Java heap space` every 3 days. How do you isolate the root cause?"*

**Step-by-Step Response**:
1. **Verify Metrics**: Inspect JVM memory graphs in Prometheus/Grafana. Confirm that after each GC cycle, the baseline "floor" memory of Old Generation steadily increases (sawtooth pattern with rising baseline).
2. **Obtain Heap Dump**: Capture heap dump safely via `-XX:+HeapDumpOnOutOfMemoryError` or during business lulls with `jcmd <pid> GC.heap_dump /tmp/dump.hprof`.
3. **Analyze with Eclipse MAT**:
   - Open `.hprof` in Eclipse Memory Analyzer Tool (MAT).
   - Generate the **Dominator Tree** and **Leak Suspects Report**.
   - Inspect top objects by **Retained Size** (memory kept alive by this object vs. Shallow Size).
   - Check the **Shortest Path to GC Roots** to identify what is keeping the objects alive (e.g., unbounded static `HashMap`, unremoved `ThreadLocal` variables in thread pools, unclosed database connection streams).
4. **Fix & Verify**: Apply fix (e.g., implement bounded cache with TTL or clean `ThreadLocal.remove()` in a filter/interceptor) and run a load test to verify flat GC memory retention.

---

### Scenario 2: Troubleshooting High CPU Usage (100% CPU Spike)
**Interview Question**: *"A Java process spikes to 100% CPU on a production Linux node. Walk me through the exact CLI diagnostic commands."*

**Step-by-Step Response**:
1. **Find the Process ID**:
   ```bash
   top
   # Identify Java PID (e.g., PID = 24500)
   ```
2. **Identify the Specific Culprit Thread (LWP)**:
   ```bash
   top -H -p 24500
   # Identify highest CPU consuming thread ID (e.g., Thread ID = 24520)
   ```
3. **Convert Thread ID to Hexadecimal**:
   ```bash
   printf "0x%x\n" 24520
   # Output: 0x5fd0
   ```
4. **Capture and Search Thread Dump**:
   ```bash
   jstack 24500 > /tmp/threaddump.txt
   grep -A 30 "0x5fd0" /tmp/threaddump.txt
   ```
5. **Analyze Code Path**: Inspect the stack trace for infinite loops, regex catastrophic backtracking (`Pattern.compile`), or intense lock contention loops.
